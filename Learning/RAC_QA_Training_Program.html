Program Overview

Program Philosophy

This QA Training Program is designed specifically for the Palawan Group of Companies IT Department. We do not train for theory alone. We train for real work — the kind of testing that happens every sprint, every release, and every deployment in our environment.

Week 1  |  8 Hours  |  Level 1 Foundation

Module Objective

Build absolute clarity on what Software Quality Assurance is, why it exists, and where it fits in the software development process. Participants must leave this module thinking like a tester, not like a user.

Key Concepts

ConceptDefinition
Quality AssuranceProcess-oriented. Prevents defects. Entire team is responsible. Proactive.
Quality ControlProduct-oriented. Finds defects. QA team responsible. Reactive.
Verification"Are we building the product right?" — checks process, reviews, walkthroughs
Validation"Are we building the right product?" — checks product meets user needs
ErrorHuman mistake made by developer (e.g., wrong formula used)
Defect / BugFlaw in software caused by an error
FailureSystem produces incorrect output when defect is executed in production
Black Box TestingTester does NOT know internal code. Tests based on inputs/outputs only.
White Box TestingTester HAS access to code. Tests internal logic, paths, branches.

Hands-on Exercise

Live Bug Hunt: Open the RAC QA Practice App. Split into groups. Each group has 15 minutes to find as many bugs as possible. Teams present findings. Discuss: which are functional? Non-functional? UI bugs?

Interview Questions to Practice

  • What is the difference between Quality Assurance and Quality Control?
  • Explain the difference between Verification and Validation with real examples.
  • What is a defect lifecycle? Name all stages.
  • What is the difference between a bug, defect, error, and failure?
  • Name 5 non-functional testing types and explain when each is used.

Assignment

  • Research and document 2 real-world software failures from the last 5 years. Write a 1-page bug impact analysis for each.
  • Create a comparison table: Manual Tester vs QA Engineer vs QA Supervisor — roles, skills, tools.
  • Quiz: 20-question MCQ on QA fundamentals — minimum 80% to pass.
Milestone Checkpoint: Module 1 Complete — Participant can define QA, explain testing types, and articulate the tester role clearly.

Module 3 — Test Case Design Techniques

Week 2  |  10 Hours  |  Level 2 Core Manual

Module Objective

Test case design is the core skill of a QA engineer. Participants must master all major design techniques and write test cases at professional quality — the kind that survives peer review and audit.

Test Case Structure — PGC Standard Format

FieldDescription
Test Case IDUnique identifier (e.g., TC_LOGIN_001)
Test Case TitleShort, clear description of what is being tested
Module / FeatureWhich area of the application this belongs to
Pre-conditionsWhat must be true before this test can be executed
Test StepsNumbered, clear, atomic steps to reproduce the test
Test DataSpecific input data required
Expected ResultWhat the system SHOULD do (based on requirements)
Actual ResultWhat the system DID do (filled during execution)
StatusPass / Fail / Blocked / Not Executed
PriorityCritical / High / Medium / Low

Design Techniques

TechniqueWhen to UseExample
Equivalence Class Partitioning (ECP)Large input range — reduce test casesAge field (18–60): test 25 (valid), 10 (low invalid), 70 (high invalid)
Boundary Value Analysis (BVA)Numeric inputs with defined boundariesQuantity (1–100): test 0, 1, 2, 99, 100, 101
Decision TableMultiple conditions determine outcomeLogin: Username valid/invalid x Password valid/invalid = 4 test cases
State TransitionSystem moves through statesTransaction: Pending → Approved → Completed → Cancelled
Error GuessingExperience-based, exploratoryEmpty fields, spaces, SQL chars, very long input, negative numbers

  • Write 10 test cases for the Password field using all techniques
  • Peer review: swap test cases with a partner and find gaps in coverage

Assignment

  • Write 30 test cases for the Transaction Form module using ECP, BVA, and Error Guessing
  • Create a Decision Table for the Login module (valid/invalid email x valid/invalid password)

Milestone Checkpoint: Module 3 Complete — Participant can write 30+ professional test cases for any feature using industry-standard design techniques.

Module 6 — API Testing with Postman

Week 4  |  10 Hours  |  Level 2 Core Manual

Module Objective

API testing is the most critical differentiator between a junior and mid-level QA in 2026. Every company expects QA engineers to know at least basic Postman. This module covers API testing comprehensively.

HTTP Methods QA Must Know

MethodPurposeExample
GETRetrieve data from serverGET /api/users/123 — returns user profile
POSTCreate new resourcePOST /api/transactions — creates a new transaction
PUTUpdate entire resourcePUT /api/users/123 — replaces entire user record
PATCHPartial updatePATCH /api/users/123 — updates only specified fields
DELETERemove resourceDELETE /api/transactions/456 — deletes the transaction

HTTP Status Codes to Verify

CodeMeaningWhen to Expect It
200 OKRequest successfulSuccessful GET, PUT, PATCH
201 CreatedResource createdSuccessful POST
400 Bad RequestInvalid request dataMissing required fields, wrong format
401 UnauthorizedNot authenticatedNo token or expired token
403 ForbiddenNot authorizedValid token but insufficient permissions
404 Not FoundResource does not existWrong ID or endpoint
500 Internal Server ErrorServer-side errorBug in backend code

API Test Scenarios to Execute

  • Happy Path: Valid request with correct data — verify 200 OK and correct response body
  • Invalid Data: Send wrong data types, missing required fields — verify 400 Bad Request
  • Authentication: Test without token — verify 401 Unauthorized
  • Authorization: Test with valid token but wrong role — verify 403 Forbidden
  • Not Found: Request non-existent resource — verify 404 Not Found
  • Response Validation: Verify response body structure, all required fields present, data types correct
  • Response Time: Every API should respond in < 2 seconds under normal load

Assignment

  • Install Postman. Test the public API: https://reqres.in — write 15 test cases covering GET, POST, PUT, DELETE
  • Write API test cases for a Login API — positive case, wrong password, missing body
  • Create a Postman Collection for all CRUD operations and export it
Milestone Checkpoint: Module 6 Complete — Participant can test APIs with Postman and validate response codes, body, and response time.

Module 7 — Database Testing & SQL Basics

Week 5  |  8 Hours  |  Level 2 Core Manual

Module Objective

After any user action in the UI, QA must verify the database reflects the correct change. This is called backend verification — critical for data integrity testing.

Essential SQL Queries for QA

QA Action (UI)Database Verification Query
User registers with emailSELECT * FROM users WHERE email='newuser@test.com' — verify record exists
Transaction submittedSELECT * FROM transactions WHERE ref_no='TXN-001' — verify record created
Profile updatedSELECT * FROM users WHERE id=1 — verify updated fields
Record deletedSELECT * FROM records WHERE id=X — verify soft delete flag or record gone

Database Testing Checklist

  • CRUD Verification: After every Create/Update/Delete action in UI, verify the corresponding DB change with SQL
  • Null Constraints: Mandatory fields should not allow NULL in the database
  • Unique Constraints: Email, phone, transaction ID — verify DB rejects duplicates
  • Default Values: Fields with default values — verify they are set correctly
  • Data Type Validation: Amount field should be DECIMAL, not VARCHAR
  • Referential Integrity: Deleting a parent record should handle child records correctly

Assignment

  • Write 15 SQL queries to verify backend data after UI actions in the RAC QA Practice App
  • Create a database verification checklist for the Transaction Form module
  • Practice SQL on https://www.sqlfiddle.com — complete all exercises in the provided SQL exercise sheet
Milestone Checkpoint: Module 7 Complete — Participant can write SQL queries and validate backend data after UI actions.

Module 9 — Performance Testing with JMeter

Week 9–10  |  12 Hours  |  Level 4 Performance

Module Objective

Performance testing ensures the system can handle the expected number of users without degradation. This module covers JMeter installation, test design, execution, and result analysis — aligned with PGC's load testing process.

Key Performance Metrics

MetricDefinitionTarget
Response TimeTime from request to complete response (ms)< 500ms (95th pct)
Throughput (TPS)Requests processed per secondScales with users
Error Rate% of failed requests< 1%
APDEX ScoreUser satisfaction score (0–1)> 0.85
90th Percentile90% of users get response faster than this< 1 second

JMeter Test Plan Structure

  • Thread Group: Define concurrent users, ramp-up period, duration
  • HTTP Request Sampler: Define the API endpoint to test
  • HTTP Header Manager: Add authentication headers
  • Timer: Add think time between requests (Uniform Random Timer)
  • Listeners: View Results Tree, Aggregate Report (disable during actual tests)

Running a Load Test

# Run test and generate HTML report
jmeter -n -t test_script.jmx -l results.jtl -e -o report_output

# Generate report from existing results
jmeter -g results.jtl -o report_output

Reading the HTML Report

SectionWhat to Look For
APDEX TableScore should be > 0.85. Lower = poor user experience.
Statistics TableCheck error %, average, 90th/95th/99th percentiles, throughput
Errors SectionIdentify error types (503, 504, ConnectionClosedException)
Response Times Over TimeShould be flat/stable. Spikes = bottlenecks.
Transactions per SecondShould increase with load. Plateau = capacity ceiling.

Assignment

  • Install JMeter and run a basic load test against a public API (https://reqres.in)
  • Design a load test for 50 concurrent users, 60-second ramp-up, 5-minute duration
  • Generate an HTML report and write a 1-page analysis of the results
  • Identify the breaking point by gradually increasing users from 10 to 100
Milestone Checkpoint: Module 9 Complete — Participant can design, execute, and analyze a basic load test using JMeter.
